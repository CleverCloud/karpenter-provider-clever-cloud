# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A [Karpenter](https://karpenter.sh) cloud provider for Clever Kubernetes Engine (CKE), Clever Cloud's managed Kubernetes. It implements karpenter-core's `CloudProvider` interface on top of Clever Cloud's **in-cluster** NodeGroup API (`nodegroups.api.clever-cloud.com/v1`). There is no API token and no HTTP call to any Clever Cloud endpoint: everything goes through the cluster's own Kubernetes API (the controller needs no egress beyond the API server), and the Clever Cloud operator upstream reconciles NodeGroups into VMs. The flavor catalogue is built in and overridable per flavor through `settings.flavors`; the dynamic-pricing refresher that polled Clever Cloud's public API was removed once `/v4/kubernetes-product` started requiring authentication.

## Commands

```sh
make build       # go build -o bin/karpenter-clevercloud ./cmd/controller
make test        # go test ./pkg/... ./cmd/...
make test-envtest  # controllers against a real kube-apiserver (setup-envtest downloads binaries)
make e2e         # full suite against a live CKE cluster (E2E_CONTEXT required — docs/e2e.md)
make generate    # controller-gen: deepcopy + CleverNodeClass CRD → deploy/crds, then sync into both Helm charts
make vet         # go vet ./...
make lint        # golangci-lint v2 via go run (config in .golangci.yml, no install needed), on the Go toolchain go.mod pins like CI
make vulncheck   # govulncheck pinned by GOVULNCHECK_VERSION, run under go.mod's go directive (fetches vuln.go.dev)
make chart-lint  # helm lint + template both charts
make test-chart  # go test ./test/chart/... — the controller placement guard (fails, not skips, without helm)
make chart-package  # helm package both charts into dist/ (TAG=v<semver>; chart version = TAG without the v)
make raw-manifest   # regenerate deploy/karpenter.yaml from charts/karpenter (never edit it by hand)
make run         # build + run locally against current kubeconfig (DISABLE_LEADER_ELECTION=true)
make image       # docker build (IMAGE=, TAG= overridable)
```

Run a single test: `go test ./pkg/cloudprovider/ -run TestName`

Run `make generate` after any change to `pkg/apis/` (deepcopy), `pkg/apis/v1alpha1/` (CRD schema), or a `sigs.k8s.io/karpenter` bump. The CleverNodeClass CRD is generated; the `karpenter.sh_*.yaml` CRDs in `deploy/crds/` are synced from the pinned karpenter module (`sync-karpenter-crds` — upgrade playbook in CONTRIBUTING.md); the NodeGroup CRD is owned by Clever Cloud and not in this repo at all. Run `make raw-manifest` after any change to `charts/karpenter` templates, values, or `Chart.yaml` — `deploy/karpenter.yaml` is generated from the chart and CI fails on drift.

The chart CRD copies are generated too: `make generate` copies `deploy/crds/` verbatim into `charts/karpenter/crds/` and awk-templates them into `charts/karpenter-crd/templates/` (`sync-chart-crds`). Never edit those files by hand — CI fails if `make generate` produces a diff.

The Go patch release is pinned twice and the two must match: the `go` directive in `go.mod` (what CI installs, tests and govulncheck-scans with) and the Dockerfile's `golang:<x.y.z>` builder tag (what the shipped binary is actually built with — the golang image runs with `GOTOOLCHAIN=local`). Bump both together, to the latest patch release of the minor; `TestImageBuilderMatchesGoDirective` (`cmd/controller`) fails otherwise. Nothing bumps them automatically — the daily Govulncheck job of the CodeQL workflow (`make vulncheck`) is the trigger.

## Architecture

### The core invariant: 1 NodeClaim = 1 NodeGroup

Karpenter manages individual machines; Clever Cloud exposes groups of identical nodes. The provider bridges this by backing every `NodeClaim` with a dedicated NodeGroup with `nodeCount: 1`, **named after the NodeClaim**. Clever Cloud deterministically names the single node `<nodegroup>-node0`. Provider IDs are `clevercloud://<nodegroup-name>` (`nodegroup.ProviderID`/`ParseProviderID`). Many code paths rely on this name equality (e.g. `Delete` falls back to the NodeClaim name when there is no provider ID yet; GC matches NodeGroups to NodeClaims by name).

NodeGroups created by this provider carry the marker label `karpenter.clever-cloud.com/managed=true` (`nodegroup.IsManaged`). **Every** read/delete path checks it — NodeGroups created manually or by CKE's own autoscaler must never be touched.

### Two API groups (pkg/apis)

- `karpenter.clever-cloud.com` — provider-owned. `CleverNodeClass` in `pkg/apis/v1alpha1/` (CRD generated by `make generate`). `labels.go` registers the provider's well-known labels into karpenter-core's `v1.WellKnownLabels` via `init()`.
- `api.clever-cloud.com` — Clever Cloud-owned. `pkg/apis/nodegroup/v1/` is a hand-written typed client for their NodeGroup CRD (kept deliberately loose to avoid validation surprises on fields their operator owns). `spec.flavor/labels/taints` are immutable after creation; only `nodeCount` may change. Helpers `IsSynced()`/`IsQuotaExceeded()`/`Refusal()`/`TransientFailure()` read their condition/phase conventions. The operator reports several conditions at once (live: `Ready=True` + `ReconcileInProgress=True` + `ReconcileFailed=True(UpstreamError)`), so `ReconcileFailed` reasons are classified in one place, `transientFailureReasons`: an allowlist of failures the operator retries on its own (`UpstreamError`, a failed Clever Cloud API call); every other reason, unknown ones included, is a refusal.

### Wiring (cmd/controller/main.go)

Uses karpenter-core's `operator.NewOperator()`, registers the core controllers plus the provider's own (`pkg/controllers/controllers.go`). The CloudProvider is wrapped in `overlay.Decorate` for NodeOverlay support. Region comes from `CLEVER_CLOUD_REGION` (default `par` — CKE is single-zone today). Capacity type is always on-demand. `FLAVORS_CONFIG_PATH` (set by the chart when `settings.flavors` is non-empty) is read once at startup (`env.WithDefault*`, like every setting). Any env var the binary reads must be kept in sync between chart `values.yaml` and chart `deployment.yaml`; `deploy/karpenter.yaml` follows automatically (generated from the chart by `make raw-manifest`).

### Observability (pkg/metrics, docs/observability.md)

Provider Prometheus metrics live in `pkg/metrics` (package-level vars — operatorpkg constructors MustRegister at call time, so create each exactly once; tests read deltas via `pkg/metrics/metricstest`). The CloudProvider is wrapped in karpenter-core's `metrics.Decorate` (durations + typed errors per method). Kubernetes Events go through karpenter's `events.Recorder` (op.EventRecorder, deduping) — plumbed into the nodegroup provider (quota, acceptance timeout, on the NodeClaim) and the GC (reaped/refused, on the NodeGroup). Every failure-path metric/event and its operator action is documented in docs/observability.md — keep it in sync when adding signals.

### Provider controllers (pkg/controllers/) — each exists for a CKE quirk

- **providerid**: CKE does not set `node.spec.providerID`, but karpenter-core matches Nodes to NodeClaims through it. Stamps `clevercloud://<name>` on nodes carrying the `clever-cloud.com/nodegroup` label, only if that NodeGroup is managed, and on exactly one node per group (checked uncached against the Nodes that exist): the extra node of an externally resized group is refused, since two Nodes on one provider ID is core's terminal `MultipleNodesFound`. A refused node that carries `karpenter.sh/nodepool` (older groups' immutable `spec.labels` still hold it) has that label stripped with a merge patch — core's cluster state ignores a node with that label and no provider ID, so its first `Synced()` after a restart would never complete (provisioning and disruption frozen cluster-wide). Never stripped from the stamped node or from nodes of unmanaged groups — so an older group recreated upstream without its managed label but with its old `spec.labels` still freezes the sync; the manual remedy is in docs/observability.md.
- **garbagecollection**: safety net (every 2 min) reaping managed NodeGroups whose NodeClaim is gone. Owner references handle the normal path; this catches force-deleted NodeClaims. NodeGroups younger than 2 min are skipped (informer lag), and reaping requires the NodeClaim owner reference stamped at creation (`nodegroup.NodeClaimOwners`) — the managed label alone is forgeable by hand-copying a manifest and must never be sufficient to destroy a group, and a group is never reaped while any NodeClaim its owner references name is still alive (the mutable labels are not the identity). The same sweep fast-fails the reverse orphan: a Launched-but-unregistered NodeClaim whose NodeGroup vanished (quota engine reclaiming an accepted group) is deleted instead of burning the 15-min registration TTL — core's own GC deliberately skips unregistered claims, so that window is the provider's. Existence is checked against ALL NodeGroups (a label-stripped group must not read as vanished), and never-Synced-but-present groups are left alone (deleting mid-first-reconcile is the documented upstream reservation-leak pattern).
- **nodeclass**: CleverNodeClass validation/readiness conditions + a termination finalizer so a NodeClass can't disappear while NodeClaims reference it. `Create` refuses NodeClasses that aren't Ready. It also migrates NodeGroups stamped by an older hash generation, only when provably safe (see `IsDrifted` below).
- **instancetypecapacity**: feeds live node `status.capacity`/`allocatable` back into the instance-type provider (`RecordObservedCapacity`) so estimated catalog entries self-correct.

### Instance types (pkg/providers/instancetype)

Flavor catalog (2XS…XL); nothing is fetched at runtime. Offering prices are **not a currency** but a unitless relative cost, `RelativePrice(cpu, memoryKi) = 1/3·cpu/cpu_ref + 2/3·memoryKi/memoryKi_ref` rounded to 4 decimals, with ref = the first `FlavorSizing` entry (2XS = 1.0). karpenter-core only compares and sums prices (cheapest-first launch, consolidation savings, balanced scoring as a fraction of the NodePool total), so only the ordering matters: the 1:2 cpu:memory weighting mirrors CKE's public worker price structure (a nominal GB costs two vCPUs), and `TestRelativePriceKeepsConsolidationOrder` proves that every pair of multisets of up to 4 built-in flavors the public prices rank strictly is ranked the same way (equal weights invert 12). That holds for the built-in sizing and for a catalogue with every flavor pinned proportionately (the README example, all six at their measured memory, is tested too), not for arbitrary overrides: a cpu/memoryKi pin reprices its flavor alone against the unchanged 2XS reference, so pinning one flavor can invert comparisons (XL alone at its measured memory makes merging four small nodes into an XL that really costs more look like a saving) — hence the docs' "pin every flavor the same way, or none". The catalog served by `List()` is `ApplyOverrides(DefaultFlavors, overrides)`, computed **once** in `NewProvider`: the built-in `DefaultFlavors` seed plus a **per-flavor overlay** of optional-field `FlavorOverride`s (`name`, `cpu`, `memoryKi` — no price) loaded from `FLAVORS_CONFIG_PATH`; overrides win per field, and `ApplyOverrides` then recomputes **every** flavor's `Price` from its final cpu/memoryKi (pinning memory reprices the flavor; a base's own `Price` is never served). `FlavorSizing`/`SizingByName` is the single source of truth for sizing (cpu, kernel-visible memoryKi); `DefaultFlavors` is derived from it, prices included, and `TestDefaultFlavorsPriceTable` pins the resulting prices; `Synthesize` prices seed-known types with the same `RelativePrice`. Prices come from the catalogue sizing, never from observed capacity, so they are fixed for the controller's lifetime. Capacities for 2XS/XS/S/M were **measured on live nodes**; L/XL are derived estimates corrected at runtime by the instancetypecapacity controller. The `flavors` slice is never written after construction, so `List()`/`Get()` read it lock-free and build fresh objects on every call (karpenter-core mutates them); `mu` only guards the observed-capacity map. `cloudprovider.resolveInstanceType` picks the cheapest flavor satisfying the NodeClaim's requirements and resource requests. An override introducing a flavor outside `SizingByName` must set cpu **and** memoryKi (enforced at parse time and again in `ApplyOverrides`), which is all it is sized and priced from. Overrides are parsed strictly: an unknown key — including the `priceHourly` of earlier releases — invalidates the whole file (base catalogue, `flavors_config_invalid=1`), and the chart's `values.schema.json` refuses it at `helm` time first.

### NodeGroup lifecycle & quota (pkg/providers/nodegroup)

`Create` is deliberately conservative because the CKE beta quota engine misbehaves under concurrency (leaked reservations were observed during testing):

1. All creations are **serialized** through `createMu`.
2. After creating, it polls up to 15s for the upstream operator to accept (`Ready`) or refuse the group. `Ready=True` wins over any other condition: a Ready group is a booted VM and is never deleted or treated as refused, on a fresh create and on the `AlreadyExists` adoption path alike. A transient failure (`TransientFailure()`, i.e. `UpstreamError`) is not a refusal: no delete (that would land mid-first-reconcile, the reservation-leak pattern), no hold-out, no ICE — the poll keeps waiting as for any group in progress, and a log line plus a `NodeGroupTransientFailure` event surface it whatever ended the poll, `Ready` included: the failure is recorded from every status the poll reads, before the `Ready` return, since the operator keeps it set next to `Ready` (Normal if the group was then accepted within the window; Warning on a timeout, or when the launch then failed, so a vanish or refusal stays traceable to the incident). A controller shutdown is not an outcome and publishes neither this nor the timeout signal. Any other refusal is terminal whatever its reason: `QuotaExceeded` returns `ErrQuotaExceeded`, any other `ReconcileFailed` reason (`Refusal()`) returns `ErrFlavorRejected` (which additionally holds that flavor out of `resolveInstanceType` for 5 min, since karpenter-core keeps no per-offering memory of an `InsufficientCapacityError`). Both free the reservation, and a failure to free it never downgrades the refusal to success. Timeout = optimistic success (karpenter's 15-min registration TTL is the backstop).
3. On quota rejection: the NodeGroup is deleted immediately (frees the reservation), a **1-minute backoff** fails subsequent creates fast, and `ErrQuotaExceeded` is returned — which `cloudprovider.Create` maps to karpenter's `InsufficientCapacityError` so the scheduler relaxes to other options instead of waiting out the TTL.
4. Any `Delete` clears the backoff (freed capacity).

NodeGroups are created with the `karpenter.sh/unregistered:NoExecute` taint (closes the race between node readiness and karpenter's label sync) and an owner reference to their NodeClaim. Node labels pushed onto the NodeGroup are filtered (`isNodeGroupLabelAllowed`, i.e. `v1alpha1.ValidateNodeClassLabel`, the rule shared with the CRD CEL rule and the nodeclass controller) because the NodeGroup CRD rejects reserved prefixes (`kubernetes.io/`, `clever-cloud.com/`, …), and the `karpenter.sh` domain (and its subdomains) is kept out on purpose: `spec.labels` is immutable and the platform applies it to **every** node of the group, so `karpenter.sh/nodepool` would land on nodes that never get a provider ID (an externally resized group's extra node) and wedge core's cluster-state sync. Filtered labels still reach the registered node via karpenter's registration sync; the unregistered taint keeps pods off it until then.

### CloudProvider semantics worth knowing (pkg/cloudprovider)

- `Get` treats a NodeGroup with a deletion timestamp as NotFound — the Clever Cloud finalizer needs karpenter to release the Node first, so a terminating group must look "already gone".
- `Get`/`List` **never fail on an unknown flavor** (`errors.Is(err, instancetype.ErrUnknownFlavor)` only — other errors surface): they degrade to `instancetype.Synthesize`, a name-only floor plus seed sizing when the name is known, with observed capacity overriding both. Failing List stalls core's nodeclaim GC cluster-wide; failing Get wedges node termination before drain; and *skipping* the entry in List would make core GC delete the registered NodeClaim as soon as its node is NotReady — synthesize-and-include is the only safe shape. The synthesized type never enters `GetInstanceTypes`; the node is rolled by core's `InstanceTypeNotFound` drift path under disruption budgets (semantics in docs/observability.md).
- `IsDrifted` compares the hash annotation stamped on the NodeGroup at creation (`karpenter.clever-cloud.com/clevernodeclass-hash`) **like with like**: against what the generation recorded next to it (`karpenter.clever-cloud.com/clevernodeclass-hash-version`; absent = `v1`, groups created up to v0.11.x) computes for the *current* spec (`CleverNodeClass.HashMatches`), never against today's `Hash()` — so a hash change neither drifts every node on upgrade nor hides a NodeClass edit made while the upgrade rolls out. A stamp from a generation the controller cannot compute (a newer controller's, after a rollback), or no stamp, never drifts. The nodeclass controller re-stamps an older-generation group to the current generation only when its stamp still matches the current spec and its NodeClaim is not already Drifted; otherwise the stamp stays and the node drifts. Any change to `CleverNodeClassSpec` or to the hashing needs a new generation, even an added field that leaves existing hashes alone — the steps are on `NodeClassHashVersion` (freeze the outgoing one in the append-only `previousNodeClassHashes`), enforced by `TestHashVersionPinnedToSpec` (pins the spec's fields and a hash) and `TestEveryHashGenerationIsSupported`. A frozen generation declares the spec fields it had, and `HashMatches` never matches it against a spec that sets any other field (the node was built before that field existed), so frozen generations stay correct as the spec grows (`TestFrozenGenerationsRefuseFieldsTheyDidNotHave`).
- `RepairPolicies`: `NodeReady` False/Unknown tolerated 10 min (requires the `NodeRepair` feature gate).

### Deployment artifacts (charts/, deploy/)

Two Helm charts, deliberately overlapping: `charts/karpenter` installs the controller stack and carries the CRDs in its `crds/` directory (Helm installs those but never upgrades or deletes them), while `charts/karpenter-crd` manages the **same** CRDs as regular templates so upgrades flow through Helm — users install both. `deploy/karpenter.yaml` is the raw-manifest alternative, generated from `charts/karpenter` by `make raw-manifest` (namespace + `helm template` with default values; never edit it by hand — CI fails on drift). All CRD copies originate from `deploy/crds/` via `make generate`. `charts/karpenter/values.schema.json` types only what the templates need typed (the booleans, `settings.flavors`) and deliberately tolerates unknown keys: a `--reuse-values` upgrade still carrying the removed `settings.pricing` block must keep rendering (`test/chart` pins it). The one exception is a `settings.flavors` entry, a closed object: the controller refuses a whole overrides file on an unknown key, so a leftover key (the removed `priceHourly`) must fail the upgrade instead of silently dropping every override (`test/chart` pins that too).

## Testing

Unit tests use the controller-runtime fake client (see `pkg/cloudprovider/cloudprovider_test.go` for the pattern: `fake.NewClientBuilder().WithScheme(scheme.Scheme).WithStatusSubresource(&v1alpha1.CleverNodeClass{})`). No envtest/cluster needed. Two more stages exist (`docs/e2e.md`): `make test-envtest` (`test/envtest/`, runs in PR CI) drives the controllers against a real kube-apiserver and proves the vendored CRDs install; `make e2e` (`test/e2e/`, behind the `e2e` build tag) runs the whole provider against a live CKE cluster and REQUIRES `E2E_CONTEXT` — it creates real hourly-billed VMs, cleans up after itself, and `hack/e2e-cleanup.sh` is the no-controller fallback sweep. The e2e stage is **local-only by policy**: CKE test clusters are ephemeral (destroyed at the end of a working session) and their cluster-admin kubeconfigs must never land in GitHub Actions secrets — do not wire `make e2e` into any workflow. `docs/E2E-RESULTS.md` records the original manual validation runs — behavioral claims in the README (provisioning times, quota behavior, measured capacities) come from there and the e2e wait bounds derive from its timing envelope.

## CI

PRs run `make vet`, `make build`, `make chart-lint`, `make test-chart`, a generated-files drift check (`make generate raw-manifest` must produce no diff), `make test`, `go test -race ./pkg/... ./cmd/...`, `make test-envtest`, golangci-lint (`ci-lint.yaml` — same version as `make lint`, which also runs it on the go.mod toolchain CI uses: a newer local Go's standard library can change findings or crash the analyzers), CodeQL and `make vulncheck` (`codeql-analysis.yaml`, also daily — govulncheck is a separate job so a vulnerability finding can never skip CodeQL), and a git-hygiene gate (`git.yaml`: every commit message must be a Conventional Commit, no `fixup!`/`squash!` commits). Pushing a `v*` tag builds the image, pushes it to ghcr.io, and publishes both Helm charts as OCI artifacts to `oci://ghcr.io/<owner>/<repo>/charts/{karpenter,karpenter-crd}` (chart version = tag without the `v` prefix, appVersion = tag — the in-repo `Chart.yaml` versions are placeholders overridden at package time, but the release fails fast if they lag the tag: bump both files and run `make raw-manifest` in the release commit). Commit conventions are documented in CONTRIBUTING.md.

## Operational constraints that shape the code

- Org quota defaults to 40 vCPU / 40 GB RAM **including the control plane**; quota rejections are normal operation, not errors.
- Provisioning takes ~40–90 s; deletion ~40 s.
- The controller must run on nodes karpenter does not manage. The chart (and the `deploy/karpenter.yaml` generated from it) enforces that with a required node affinity on `karpenter.sh/nodepool` **DoesNotExist** — karpenter-core stamps that label on every node it provisions (at registration) and on no other, so the rule holds on `ALL_IN_ONE` (schedulable in-cluster control-plane node), on `DEDICATED_COMPUTE`/`DISTRIBUTED` (control plane outside the cluster, only worker nodes) and on any topology added later. Never re-encode a specific topology's node label as a default: `clever-cloud.com/cluster-node-role: control-plane` was that bug, and `test/chart` fails if it comes back. Before registration, and for good on a resized group's extra node, the node lacks the label and only the `karpenter.sh/unregistered:NoExecute` taint keeps the controller off, so the chart's default tolerations must never cover it (also pinned by `test/chart`).
- Don't enable CKE's own `autoscalingEnabled` alongside this provider (two autoscalers fighting).
