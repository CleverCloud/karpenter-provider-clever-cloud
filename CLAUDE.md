# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A [Karpenter](https://karpenter.sh) cloud provider for Clever Kubernetes Engine (CKE), Clever Cloud's managed Kubernetes. It implements karpenter-core's `CloudProvider` interface on top of Clever Cloud's **in-cluster** NodeGroup API (`nodegroups.api.clever-cloud.com/v1`). There is no API token and no HTTP call to any Clever Cloud endpoint: everything goes through the cluster's own Kubernetes API (the controller needs no egress beyond the API server), and the Clever Cloud operator upstream reconciles NodeGroups into VMs. The flavor catalogue is built in and overridable per flavor through `settings.flavors`; the dynamic-pricing refresher that polled Clever Cloud's public API was removed once `/v4/kubernetes-product` started requiring authentication.

Run `make generate` after any change to `pkg/apis/` (deepcopy), `pkg/apis/v1alpha1/` (CRD schema), or a `sigs.k8s.io/karpenter` bump. The CleverNodeClass CRD is generated; the `karpenter.sh_*.yaml` CRDs in `deploy/crds/` are synced from the pinned karpenter module (`sync-karpenter-crds` — upgrade playbook in CONTRIBUTING.md); the NodeGroup CRD is owned by Clever Cloud and not in this repo at all. The Go patch release is pinned twice and the two must match: the `go` directive in `go.mod` (what CI installs, tests and govulncheck-scans with) and the Dockerfile's `golang:<x.y.z>` builder tag (what the shipped binary is actually built with — the golang image runs with `GOTOOLCHAIN=local`). Bump both together, to the latest patch release of the minor; `TestImageBuilderMatchesGoDirective` (`cmd/controller`) fails otherwise. Nothing bumps them automatically — the daily Govulncheck job of the CodeQL workflow (`make vulncheck`) is the trigger.

## Architecture

### The core invariant: 1 NodeClaim = 1 NodeGroup

Karpenter manages individual machines; Clever Cloud exposes groups of identical nodes. The provider bridges this by backing every `NodeClaim` with a dedicated NodeGroup with `nodeCount: 1`, **named after the NodeClaim**. Clever Cloud deterministically names the single node `<nodegroup>-node0`. Provider IDs are `clevercloud://<nodegroup-name>` (`nodegroup.ProviderID`/`ParseProviderID`). Many code paths rely on this name equality (e.g. `Delete` falls back to the NodeClaim name when there is no provider ID yet; GC matches NodeGroups to NodeClaims by name).

NodeGroups created by this provider carry the marker label `karpenter.clever-cloud.com/managed=true` (`nodegroup.IsManaged`). **Every** read/delete path checks it — NodeGroups created manually or by CKE's own autoscaler must never be touched.

### Two API groups (pkg/apis)

- `karpenter.clever-cloud.com` — provider-owned. `CleverNodeClass` in `pkg/apis/v1alpha1/` (CRD generated by `make generate`). `labels.go` registers the provider's well-known labels into karpenter-core's `v1.WellKnownLabels` via `init()`.
- `api.clever-cloud.com` — Clever Cloud-owned. `pkg/apis/nodegroup/v1/` is a hand-written typed client for their NodeGroup CRD (kept deliberately loose to avoid validation surprises on fields their operator owns). `spec.flavor/labels/taints` are immutable after creation; only `nodeCount` may change. Helpers `IsSynced()`/`IsQuotaExceeded()`/`Refusal()`/`IsRefused()`/`TransientFailure()` read their condition/phase conventions (`IsRefused` = quota or any other terminal refusal). The operator reports several conditions at once (live: `Ready=True` + `ReconcileInProgress=True` + `ReconcileFailed=True(UpstreamError)`), so `ReconcileFailed` reasons are classified in one place, `transientFailureReasons`: an allowlist of failures the operator retries on its own (`UpstreamError`, a failed Clever Cloud API call); every other reason, unknown ones included, is a refusal.

### Wiring (cmd/controller/main.go)

Uses karpenter-core's `operator.NewOperator()`, registers the core controllers plus the provider's own (`pkg/controllers/controllers.go`). The CloudProvider is wrapped in `overlay.Decorate` for NodeOverlay support. Region comes from `CLEVER_CLOUD_REGION` (default `par` — CKE is single-zone today); it is advertised as both `topology.kubernetes.io/region` and `topology.kubernetes.io/zone`. Capacity type is always on-demand. `FLAVORS_CONFIG_PATH` (set by the chart when `settings.flavors` is non-empty) is read once at startup (`env.WithDefault*`, like every setting). Any env var the binary reads must be kept in sync between chart `values.yaml` and chart `deployment.yaml`; `deploy/karpenter.yaml` follows automatically (generated from the chart by `make raw-manifest`).

### Observability (pkg/metrics, docs/observability.md)

Provider Prometheus metrics live in `pkg/metrics` (package-level vars — operatorpkg constructors MustRegister at call time, so create each exactly once; tests read deltas via `pkg/metrics/metricstest`). The CloudProvider is wrapped in karpenter-core's `metrics.Decorate` (durations + typed errors per method). Kubernetes Events go through karpenter's `events.Recorder` (op.EventRecorder, deduping) — plumbed into the nodegroup provider (quota, acceptance timeout, on the NodeClaim), the GC (reaped/refused, on the NodeGroup) and the nodegroupstatus controller (late refusal, transient failure, sync overdue, on the NodeClaim). Every failure-path metric/event and its operator action is documented in docs/observability.md — keep it in sync when adding signals.

### Provider controllers (pkg/controllers/) — each exists for a CKE quirk

- **providerid**: CKE does not set `node.spec.providerID`, but karpenter-core matches Nodes to NodeClaims through it. Stamps `clevercloud://<name>` on nodes carrying the `clever-cloud.com/nodegroup` label, only if that NodeGroup is managed, and on exactly one node per group (checked uncached against the Nodes that exist): the extra node of an externally resized group is refused, since two Nodes on one provider ID is core's terminal `MultipleNodesFound`. A refused node that carries `karpenter.sh/nodepool` (older groups' immutable `spec.labels` still hold it) has that label stripped with a merge patch — core's cluster state ignores a node with that label and no provider ID, so its first `Synced()` after a restart would never complete (provisioning and disruption frozen cluster-wide). Never stripped from the stamped node or from nodes of unmanaged groups — so an older group recreated upstream without its managed label but with its old `spec.labels` still freezes the sync; the manual remedy is in docs/observability.md.
- **garbagecollection**: safety net (every 2 min) reaping managed NodeGroups whose NodeClaim is gone. Owner references handle the normal path; this catches force-deleted NodeClaims. NodeGroups younger than 2 min are skipped (informer lag), and reaping requires the NodeClaim owner reference stamped at creation (`nodegroup.NodeClaimOwners`) — the managed label alone is forgeable by hand-copying a manifest and must never be sufficient to destroy a group, and a group is never reaped while any NodeClaim its owner references name is still alive (the mutable labels are not the identity). The same sweep fast-fails the reverse orphan: a Launched-but-unregistered NodeClaim whose NodeGroup vanished (quota engine reclaiming an accepted group) is deleted instead of burning the 15-min registration TTL — core's own GC deliberately skips unregistered claims, so that window is the provider's. Since the acceptance poll ends at the operator's decision (~1 s after creation), this sweep is what fails a group that vanishes after its acknowledgement: 2–4 min after the claim's creation (claims younger than 2 min are skipped), and without recording the quota rejection of its flavor that the poll's vanish path records (NodeGroup lifecycle step 3). Existence is checked against ALL NodeGroups (a label-stripped group must not read as vanished), and never-Synced-but-present groups are left alone (deleting mid-first-reconcile is the documented upstream reservation-leak pattern).
- **nodeclass**: CleverNodeClass validation/readiness conditions + a termination finalizer so a NodeClass can't disappear while NodeClaims reference it. `Create` refuses NodeClasses that aren't Ready or are terminating, checked under the creation lock. Labels are validated with `v1alpha1.ValidateNodeClassLabel`, except the keys v0.12.0 admitted that the rule now rejects (subdomained `kubernetes.io/`, the `karpenter.sh` domain — `IsLegacyNodeClassLabel`): failing those would stop provisioning on upgrade, so the NodeClass stays Ready, the keys are filtered from the payload like any rejected key, and they are reported by the `LabelsIgnored` condition (deliberately not a readiness dependent) plus a deduped `LabelsIgnored` Warning event. The hash migration (below) runs before they are reported, because removing such a key drifts every NodeGroup still stamped by an older generation (v2 hashed it): the condition advises drift-free removal (reason `LegacyLabelKeys`) only when `migrateHashVersion` left no NodeGroup of the NodeClass on a known older generation, and otherwise says `HashMigrationPending` with that count (stamp mismatch, NodeClaim already Drifted, failed read or write; unknown when the list fails) and is rechecked every minute. The CRD CEL rule still refuses them on new objects and on any edit of `spec.labels` that keeps them (validation ratcheting admits the unchanged map; proven in `test/envtest`). In those two domains the tolerance is v0.12.0's rule exactly (not the three prefixes, value ≤ 63 characters) whatever the label syntax, which v0.12.0 never checked: it dropped a subdomained `kubernetes.io/` key before anything validated it, so `app.kubernetes.io/part-of: My Platform` provisioned. Everything else stays fatal: what v0.12.0 refused itself, and invalid syntax on a key the payload carries (an invalid value failed v0.12.0 launches at the NodeGroup CRD's value pattern too; an invalid key is assumed to have failed — the NodeGroup CRD checks no key syntax, the apiserver refuses it on the Node — but that is not measured on CKE). It also migrates NodeGroups stamped by an older hash generation, only when provably safe (see `IsDrifted` below).
- **nodegroupstatus**: `Create` reads the operator's status only until its decision (the first status write, ~1 s after creation), while the VM comes up well after it (live: Synced at 38–58 s; one group stayed `Creating` 6 min 30 s), so a late refusal, a stuck first reconcile or a silent operator used to surface only at core's 15-min registration timeout. This watch (managed NodeGroups, plus a NodeClaim watch mapped to the group of the same name, since `Launched`/`Registered` land on the claim) follows a group while the NodeClaim it was launched for is Launched and not Registered. Ready wins, as in the poll. A terminal refusal (`IsRefused`: `IsQuotaExceeded` or `Refusal`) fails the launch: confirmed with uncached reads, the NodeClaim is deleted with uid + resourceVersion preconditions (a claim that registered in between is left alone; a Registered claim is never touched), then `nodegroup.Provider.RecordLateRefusal` arms the quota backoff or holds the flavor out, counts it and publishes the usual event; core's termination deletes the group. A transient failure is only surfaced (`NodeGroupTransientFailure`, sharing the poll's dedupe key). A group still unsynced `syncOverdueAfter` (5 min, several times the slowest healthy launch; up to 10 min before core's TTL, which counts from the claim's creation while the clock here starts at the group's, later by the claim's wait on `createMu`) after its creation is counted by the `nodegroup_sync_overdue` gauge (an in-memory set, leader-local) and surfaced as `NodeGroupSyncOverdue`; the time check uses `RequeueAfter`. Same identity rules as the GC: managed label + the NodeClaim owner reference naming the group's own name, the claim's provider ID naming the group, claims of other providers untouched.
- **instancetypecapacity**: feeds live node `status.capacity`/`allocatable` back into the instance-type provider (`RecordObservedCapacity`) so the catalogue follows what the current node image exposes. A kubelet can rewrite its own Node's `clever-cloud.com/*` labels and status (NodeRestriction does not cover that domain), so no label is trusted alone: the node's **name** — bound to its kubelet's credential by the node authorizer, and `<nodegroup>-node<N>` on CKE (`nodegroup.NodeGroupOfNode`) — must place it in the NodeGroup its `clever-cloud.com/nodegroup` label names, that group must be **managed**, and the node's flavor label must equal the group's immutable `spec.flavor`. A node claiming a managed group it is not a node of, or contradicting its flavor, is refused. Refusals (those two, plus out-of-bounds figures from the provider) tick `instancetype_observed_capacity_rejections_total` on every reconcile and are logged at most hourly per node; an accepted report more than 1% off the catalogue entry is logged once per flavor (the node image moved). Nodes whose label names no managed group (fixed nodegroups, control plane) are skipped silently. Residual risk, by design: the kubelet of a node of a managed group can move its own group's flavor within the 10% bounds (down for the process lifetime through the minimum; up until a smaller node of that flavor reports).

### Instance types (pkg/providers/instancetype)

Flavor catalog (2XS…XL); nothing is fetched at runtime. Offering prices are **not a currency** but a unitless relative cost, `RelativePrice(cpu, memoryKi) = 1/3·cpu/cpu_ref + 2/3·memoryKi/memoryKi_ref` rounded to 4 decimals, with ref = the first `FlavorSizing` entry (2XS = 1.0). karpenter-core only compares and sums prices (cheapest-first launch, consolidation savings, balanced scoring as a fraction of the NodePool total), so only the ordering matters: the 1:2 cpu:memory weighting mirrors CKE's public worker price structure (a nominal GB costs two vCPUs), and `TestRelativePriceKeepsConsolidationOrder` proves that every pair of multisets of up to 4 built-in flavors the public prices rank strictly is ranked the same way (equal weights invert 12). That holds for the built-in sizing and for a catalogue with every flavor pinned proportionately (all six pinned to the previous node image's memory, the shape of the README example, is tested too), not for arbitrary overrides: a cpu/memoryKi pin reprices its flavor alone against the unchanged 2XS reference, so pinning one flavor can invert comparisons (XL alone 5% below its built-in memory makes merging four small nodes into an XL that really costs more look like a saving; XL alone at the previous image's memory misses a real merge into it) — hence the docs' "pin every flavor the same way, or none". The catalog served by `List()` is `ApplyOverrides(DefaultFlavors, overrides)`, computed **once** in `NewProvider`: the built-in `DefaultFlavors` seed plus a **per-flavor overlay** of optional-field `FlavorOverride`s (`name`, `cpu`, `memoryKi` — no price) loaded from `FLAVORS_CONFIG_PATH`; overrides win per field, and `ApplyOverrides` then recomputes **every** flavor's `Price` from its final cpu/memoryKi (pinning memory reprices the flavor; a base's own `Price` is never served). `FlavorSizing`/`SizingByName` is the single source of truth for sizing (cpu, kernel-visible memoryKi); `DefaultFlavors` is derived from it, prices included, and `TestDefaultFlavorsPriceTable` pins the resulting prices; `Synthesize` prices seed-known types with the same `RelativePrice`. Prices come from the catalogue sizing, never from observed capacity, so they are fixed for the controller's lifetime. All six seed capacities were **measured on live nodes** (2026-09-30, Kubernetes 1.37.0, kernel 7.2.8 — `TestSeedMatchesMeasuredNodes` pins the table, docs/E2E-RESULTS.md records it); the kernel-visible memory moves with Clever Cloud's node image (current nodes expose 4.4–5.0% less than the previous seed claimed, which made karpenter launch nodes the pods did not fit on), and the e2e Provision scenario fails when a live node strays more than 1% from the seed. `RecordObservedCapacity` bounds every report against the catalogue entry **as served** (overrides included; the sizing seed for a known flavor the catalogue does not serve; consistency checks only for a flavor with neither, which only feeds `Synthesize`): cpu capacity must be equal, memory/ephemeral-storage/pods capacity and every allocatable figure within `observedTolerance` (10%), allocatable never above capacity — else `ErrImplausibleCapacity`. Accepted reports are aggregated **per resource by minimum** for the process lifetime (never last-writer-wins: order-independent, no node can raise what another lowered). The `flavors` slice is never written after construction, so `List()`/`Get()` read it lock-free and build fresh objects on every call (karpenter-core mutates them); `mu` only guards the observed-capacity map. `cloudprovider.resolveInstanceType` picks the cheapest **available** flavor satisfying the NodeClaim's requirements and resource requests, over the same catalogue `GetInstanceTypes` serves (availability: NodeGroup lifecycle step 3). Every instance type declares `topology.kubernetes.io/region` **and** `/zone` (both = the configured region) in its requirements and in its offering, and `buildNodeClaim` turns every single-valued requirement into a NodeClaim label — core's registration sync copies those onto the node, the **only** path any well-known label takes there (the platform sets no topology labels; core never derives well-known labels from requirements). Never drop one: core admits a pod/volume requiring an undeclared well-known label onto a *new* claim (`AllowUndefinedWellKnownLabels`) but checks in-flight and existing nodes strictly (`existingnode.go`), so each provisioning pass launches another VM for the same pod (reproduced live with a region nodeSelector), and a NodePool requiring it drifts every node it launches. Adding one drifts no existing node: core's drift checks a claim's labels against the offerings with undefined well-known labels allowed (`Offerings.HasCompatible`) and otherwise only against its NodePool's requirements, so a claim launched without the new label drifts only if its NodePool requires it — pinned through core's scheduler, volume topology and drift controller in `pkg/cloudprovider/topology_test.go`. It does change pod semantics: the new nodes form one domain for that key, so a required pod anti-affinity on it binds (one replica across them) where nodes lacking the key let it through — documented under README "Topology labels". An override introducing a flavor outside `SizingByName` must set cpu **and** memoryKi (enforced at parse time and again in `ApplyOverrides`), which is all it is sized and priced from. Every override name must match `FlavorNamePattern` (`^(M|([2-9]?X)?[SL])$`, Clever Cloud's T-shirt naming; the live NodeGroup CRD's `spec.flavor` is the uppercase-only enum `2XS`…`XL`), checked in `ParseFlavorOverrides`: a name of another shape (`2xs`, `CUSTOM`) could never be created, yet it would enter the catalogue, win cheapest-first when small, and fail every launch at admission — so it invalidates the whole file, a case mismatch with a "did you mean" naming the uppercase spelling. A new name of the right shape (`2XL`) still parses, so a flavor Clever Cloud adds can be declared before a release carries it; until the CRD's enum carries it, its launches are refused at admission and it is served unavailable like a flavor the operator refused (NodeGroup lifecycle step 4). The chart's `values.schema.json` carries the same pattern (`test/chart` pins the two to agree). Overrides are parsed strictly: an unknown key — including the `priceHourly` of earlier releases — invalidates the whole file (base catalogue, `flavors_config_invalid=1`), and the chart's `values.schema.json` refuses it at `helm` time first.

### NodeGroup lifecycle & quota (pkg/providers/nodegroup)

`Create` is deliberately conservative because the CKE beta quota engine misbehaves under concurrency (leaked reservations were observed during testing):

1. All creations are **serialized** through `createMu`, held until the operator's decision on the group (step 2), ~1–2 s per launch — never until `Ready`: that outlasted the window on every healthy launch, serialized launches 15 s apart, and kept core's `Cluster.Synced()` false (a NodeClaim without a provider ID) for the whole queue, freezing disruption cluster-wide and eating the registration TTL of queued claims. What a launch creates is decided **under** `createMu`, right before the POST, never before the wait: `ResolveAndCreate` runs the caller's `Resolver` (NodeClass + flavor) once it holds the lock (`Create(nodeClass, flavor)` is the fixed-argument form), and `cloudprovider.Create` passes one that re-checks everything (see CloudProvider semantics). Checked before the wait, a queued launch POSTed the flavor the launch ahead had just seen refused, launched from a NodeClass deleted meanwhile, and created a billed VM for a NodeClaim deleted meanwhile (core only branches to finalize at the start of a reconcile). A resolver runs with `createMu` held, so it must never create a NodeGroup itself.
2. After creating, it polls (1 s interval, 15-s window) for the upstream operator's **decision**, which is its first status write (measured live ~1 s after creation), not `Ready` (38–58 s). `Ready=True` wins over any other condition (returns accepted): a Ready group is a booted VM and is never deleted or treated as refused, on a fresh create and on the `AlreadyExists` adoption path alike. Then refusals, terminal whatever their reason: `QuotaExceeded` (live: written directly, never preceded by `Creating`) returns `ErrQuotaExceeded`, any other `ReconcileFailed` reason (`Refusal()`) returns `ErrFlavorRejected` (which additionally holds that flavor alone out for 5 min — served unavailable, step 3). Both free the reservation, and a failure to free it never downgrades the refusal to success. Then `ReconcileInProgress=True` (`IsReconciling()`; live: `phase: Creating`) is the **acknowledgement**: accepted, return at once and release `createMu`. Accepted either way (Ready or acknowledged) runs `clearFlavorRejection` on the group's own flavor, which ends only a hold-out recorded before this launch's create call: each hold-out carries a sequence number (`recordFlavorRejection`), the launch takes `holdOutMark` just before the create call, and a newer hold-out survives — typically the late refusal of an earlier acknowledged group (`RecordLateRefusal`, without `createMu`) recorded while this launch was polled, which an acknowledgement proves nothing about. A transient failure (`TransientFailure()`, i.e. `UpstreamError`) is not a refusal: no delete (that would land mid-first-reconcile, the reservation-leak pattern), no hold-out, no ICE; next to `ReconcileInProgress` the group is acknowledged, alone it is no decision and the poll keeps waiting. A log line plus a `NodeGroupTransientFailure` event surface it whatever ended the poll, `Ready` included: the failure is recorded from every status the poll reads, before anything can end the poll, since the operator keeps it set next to `Ready` (Normal only if the group was Ready; Warning when merely acknowledged, on a timeout, or when the launch then failed, so a vanish or refusal stays traceable to the incident). A controller shutdown is not an outcome and publishes neither this nor the timeout signal. No status yet keeps polling (a not-yet-seen group is informer lag; seen-then-gone is `ErrNodeGroupVanished`, and so is a group seen with a deletion timestamp, checked before `Ready` since a terminating group is going away whatever its status says — reachable on the adoption path). The poll only watches for a vanish until the decision; after the acknowledgement the GC sweep catches it instead (see garbagecollection). Timeout = the operator did not even acknowledge the group: optimistic success, counted by `acceptance_timeouts_total` + a `NodeGroupAcceptanceTimeout` event (a healthy launch never produces either; the e2e Provision scenario asserts a zero delta), with karpenter's 15-min registration TTL as the backstop. Once core marks the claim Launched, the nodegroupstatus controller follows the group until it syncs, fails the launch on a refusal published after the poll, and reports a group still unsynced after 5 min.
3. On quota rejection: the NodeGroup is deleted immediately (frees the reservation) and `ErrQuotaExceeded` is returned, which `cloudprovider.Create` maps to karpenter's `InsufficientCapacityError` so core deletes the claim and re-plans instead of waiting out the TTL. Core keeps **no** memory of that error (its only consumers are the launch controller's event + claim deletion and the metrics decorator) and re-plans over the same offerings: `Offering.Available` is the **only** channel back to its scheduler. So the rejection is recorded per flavor and covers the rejected flavor for a **1-minute backoff** (`nodegroup.QuotaBackoff`) and every other flavor **at least as large** in vCPUs *and* memory for **two** (`quotaRejection.coverage`; `instancetype.Sizing.AtLeast`, sized by the `Catalogue` — the `*instancetype.Provider` — given to `nodegroup.NewProvider`; a flavor it cannot size, or any flavor with a nil catalogue, is covered by its own rejection only). The second window makes the rejected flavor, the cheapest probe of freed capacity, reopen alone; the larger ones follow a window later unless that probe is rejected again. Do not collapse the two: the smallest flavor's rejection covers every other one, so a single window reopened the whole catalogue at once and each window on an exhausted quota walked down it again, one real upstream rejection per flavor size (`TestExhaustedQuotaCostsOneRejectionAWindow` pins one rejection a window after the first walk down, as the old global backoff made; a single window made it three). Both windows, and the refusal hold-out, run on the `clock.PassiveClock` given to `nodegroup.NewProvider` (`op.Clock` in `main.go`), so tests step a fake clock. `nodegroup.Provider.Unavailable` (covered flavors + hold-outs) is what `GetInstanceTypes` serves as `Available=false` and what `resolveInstanceType` reads, under `createMu` (step 1), so a claim queued behind a rejection resolves around it; `Create` still fails covered flavors fast after the resolver (a fixed-flavor caller, or a `RecordLateRefusal` — which does not take `createMu` — landing between the two). Smaller flavors stay available — they may fit. A global, size-blind backoff with always-available offerings made core rebuild the rejected claim forever (0/10 pods placed with 10 GB of headroom, through core's real scheduler: `pkg/cloudprovider/unavailable_test.go`), loop drift/consolidation replacements at the quota edge, and keep weighted NodePools from falling back past a refused flavor. The poll's vanish path (group reclaimed, or seen terminating, before the decision) and `RecordLateRefusal` feed the same state; a vanish after the acknowledgement, failed by the GC sweep, does not. Never *drop* an unavailable flavor from `GetInstanceTypes`: core's `InstanceTypeNotFound` drift checks presence (`Offerings.HasCompatible`), not availability, so dropping it would roll every node of that flavor. `Get`/`List` describe running groups from the plain catalogue, because `buildNodeClaim` takes the zone/region/capacity-type labels from the first available offering. The quota is per organisation (control plane and other clusters included): a rejection caused elsewhere is indistinguishable.
4. A create the API server refuses at admission because of its flavor (`apierrors.IsInvalid` whose only field is `spec.flavor`: the CRD's enum, reached by a `settings.flavors` name the platform does not carry yet) never reaches the operator and returns `ErrFlavorRejected` (reason `Invalid`, the API server's message) right away, before any poll: same 5-min hold-out (served unavailable, step 3), `nodegroup_rejections_total`, `NodeGroupRejected` event and ICE mapping as an operator refusal, and an error log with the full API server error. Nothing to clean up — no NodeGroup exists. As a plain error it made core retry the claim until its 5-min launch timeout and then re-plan onto the same cheapest flavor, forever. An `Invalid` that also names any other field stays a plain error (causes without a field — the `<nil>` one the API server adds when it skips the CEL rules — are ignored): it fails whatever the flavor, so holding flavors out would only walk the catalogue. A failing CEL rule is skipped once the schema fails, so it only shows on the re-plan.
5. Any `Delete` clears every quota rejection (freed capacity) — except the deletion of a group the operator refused (`IsRefused`: quota or any terminal refusal) and that never synced: its VM never came up, so it held no capacity (the acceptance poll deletes refused groups directly, bypassing `Delete`, for the same reason). That is what keeps a quota backoff armed — a late rejection's own, or another claim's — when core's termination deletes a refused group after nodegroupstatus failed its launch. `Delete` therefore takes the NodeGroup, not its name.

NodeGroups are created with the `karpenter.sh/unregistered:NoExecute` taint (closes the race between node readiness and karpenter's label sync) and an owner reference to their NodeClaim. Node labels pushed onto the NodeGroup are filtered (`isNodeGroupLabelAllowed`, i.e. `v1alpha1.ValidateNodeClassLabel`, the rule shared with the CRD CEL rule, the nodeclass controller and `CleverNodeClass.Hash()`) because the NodeGroup CRD rejects reserved prefixes (`kubernetes.io/`, `clever-cloud.com/`, …), and the `karpenter.sh` domain (and its subdomains) is kept out on purpose: `spec.labels` is immutable and the platform applies it to **every** node of the group, so `karpenter.sh/nodepool` would land on nodes that never get a provider ID (an externally resized group's extra node) and wedge core's cluster-state sync. Filtered labels still reach the registered node via karpenter's registration sync; the unregistered taint keeps pods off it until then.

### CloudProvider semantics worth knowing (pkg/cloudprovider)

- `Create` decides what it launches in `resolveLaunch`, the `nodegroup.Resolver` it hands to `ResolveAndCreate`, so under `createMu` and right before the POST (NodeGroup lifecycle step 1), in this order: the NodeClaim, read **uncached** (`apiReader`, the manager's API reader), must still exist with the same UID (another UID is a new claim of the same name, which the owner reference would not name) and no deletion timestamp — otherwise a **plain** error, deliberately neither ICE nor `NodeClassNotReadyError`, which would count a capacity/nodeclass disruption for a claim that is going away: core requeues it and finalizes it without a provider ID, so it deletes no NodeGroup (a group an earlier attempt created goes through its owner reference); the NodeClass, read uncached too, must exist (NotFound = ICE) and be Ready=True and not terminating (`NodeClassNotReadyError` — readiness conditions survive deletion, so the deletion timestamp is checked on its own); then `resolveInstanceType` picks the cheapest available flavor (ICE when none). The NodeGroup is built from the NodeClass read there (labels, hash stamp), so an edit made while the launch waited is what the node carries, not a spec that drifts at once. The returned claim is built from that resolution, i.e. from the flavor the group was created with; only the `AlreadyExists` adoption path can carry another flavor, and then the group's own flavor is described.
- `Get` treats a NodeGroup with a deletion timestamp as NotFound — the Clever Cloud finalizer needs karpenter to release the Node first, so a terminating group must look "already gone".
- `Get`/`List` **never fail on an unknown flavor** (`errors.Is(err, instancetype.ErrUnknownFlavor)` only — other errors surface): they degrade to `instancetype.Synthesize`, a name-only floor plus seed sizing when the name is known, with observed capacity overriding both. Failing List stalls core's nodeclaim GC cluster-wide; failing Get wedges node termination before drain; and *skipping* the entry in List would make core GC delete the registered NodeClaim as soon as its node is NotReady — synthesize-and-include is the only safe shape. The synthesized type never enters `GetInstanceTypes`; the node is rolled by core's `InstanceTypeNotFound` drift path under disruption budgets (semantics in docs/observability.md).
- `Hash()` covers only the NodeClass labels the NodeGroup label filter admits: labels `ValidateNodeClassLabel` rejects are left out (generation v3; v2, shipped in v0.12.0, hashed the raw labels, so removing a key no node ever received drifted the whole NodeClass). An admitted NodeClass label still counts when a NodePool label on the same key overrides it in the payload (`nodeGroupLabels` applies NodeClaim labels last): changing it drifts nodes whose payload does not change — the safe side. The rule is therefore part of the hashing: changing what it accepts needs a new generation, like a spec change. `IsDrifted` compares the hash annotation stamped on the NodeGroup at creation (`karpenter.clever-cloud.com/clevernodeclass-hash`) **like with like**: against what the generation recorded next to it (`karpenter.clever-cloud.com/clevernodeclass-hash-version`; absent = `v1`, groups created up to v0.11.x) computes for the *current* spec (`CleverNodeClass.HashMatches`), never against today's `Hash()` — so a hash change neither drifts every node on upgrade nor hides a NodeClass edit made while the upgrade rolls out. A stamp from a generation the controller cannot compute (a newer controller's, after a rollback), or no stamp, never drifts. The nodeclass controller re-stamps an older-generation group to the current generation only when its stamp still matches the current spec and its NodeClaim is not already Drifted; otherwise the stamp stays and the node drifts. Any change to `CleverNodeClassSpec` or to the hashing needs a new generation, even an added field that leaves existing hashes alone — the steps are on `NodeClassHashVersion` (freeze the outgoing one in the append-only `previousNodeClassHashes`), enforced by `TestHashVersionPinnedToSpec` (pins the spec's fields and a hash) and `TestEveryHashGenerationIsSupported`. A frozen generation declares the spec fields it had, and `HashMatches` never matches it against a spec that sets any other field (the node was built before that field existed), so frozen generations stay correct as the spec grows (`TestFrozenGenerationsRefuseFieldsTheyDidNotHave`). Frozen v1/v2 reproduce the spec as it stands: an older-generation group whose NodeClass gained or lost an undelivered key before the migration re-stamped it drifts (v3's equivalence cannot be enumerated backwards) — the conservative side.
- `RepairPolicies`: `NodeReady` False/Unknown tolerated 10 min (requires the `NodeRepair` feature gate).

### Deployment artifacts (charts/, deploy/)

Two Helm charts, deliberately overlapping: `charts/karpenter` installs the controller stack and carries the CRDs in its `crds/` directory (Helm installs those but never upgrades or deletes them), while `charts/karpenter-crd` manages the **same** CRDs as regular templates so upgrades flow through Helm — users install both. `deploy/karpenter.yaml` is the raw-manifest alternative, generated from `charts/karpenter` by `make raw-manifest` (namespace + `helm template` with default values; never edit it by hand — CI fails on drift). All CRD copies originate from `deploy/crds/` via `make generate`. `charts/karpenter/values.schema.json` types only what the templates need typed (the booleans, `settings.flavors`) and deliberately tolerates unknown keys: an upgrade still carrying the removed `settings.pricing` block (reused release values or an old values file) must keep rendering (`test/chart` pins it). The one exception is a `settings.flavors` entry, a closed object whose `name` carries the controller's `FlavorNamePattern`: the controller refuses a whole overrides file on an unknown key or a name that cannot be a Clever Cloud flavor, so a leftover key (the removed `priceHourly`) or such a name must fail the upgrade instead of silently dropping every override (`test/chart` pins both, and that the schema accepts exactly the names the controller does). Documented upgrades use `--reset-then-reuse-values` (Helm ≥ 3.14), never `--reuse-values`: the latter replaces the new chart's defaults with the previous release's, so a changed default (v0.12.0's controller placement) never reaches an upgraded install.

## Testing

Unit tests use the controller-runtime fake client (see `pkg/cloudprovider/cloudprovider_test.go` for the pattern: `fake.NewClientBuilder().WithScheme(scheme.Scheme).WithStatusSubresource(&v1alpha1.CleverNodeClass{})`). `cloudprovider.Create` reads its NodeClaim back and launches nothing for a missing one, so its tests persist the claim first (`stored`), as core does; `pkg/cloudprovider/createlock_test.go` queues launches on `createMu` (a goroutine dump tells a queued launch from one not started yet) to pin what is decided under it, and gives the provider an API reader apart from its cached client to pin that those reads bypass the informer cache. No envtest/cluster needed. When a behaviour depends on how karpenter-core reads what the provider returns, run core's own code over the fake client instead of re-deriving it: `pkg/cloudprovider/clusterstate_test.go` (core's cluster state and node informer), `topology_test.go` (core's scheduler, volume topology and nodeclaim drift controller) and `unavailable_test.go` (core's scheduler and drift controller against a fake operator and quota engine) show how. Two more stages exist (`docs/e2e.md`): `make test-envtest` (`test/envtest/`, runs in PR CI) drives the controllers against a real kube-apiserver and proves the vendored CRDs install; `make e2e` (`test/e2e/`, behind the `e2e` build tag) runs the whole provider against a live CKE cluster and REQUIRES `E2E_CONTEXT` and a target cluster with no in-cluster provider running (the suite's own controller runs with leader election disabled, so both would act) — it creates real hourly-billed VMs, cleans up after itself, and `hack/e2e-cleanup.sh` is the no-controller fallback sweep. The e2e stage is **local-only by policy**: CKE test clusters are ephemeral (destroyed at the end of a working session) and their cluster-admin kubeconfigs must never land in GitHub Actions secrets — do not wire `make e2e` into any workflow. `docs/E2E-RESULTS.md` records the original manual validation runs — behavioral claims in the README (provisioning times, quota behavior, measured capacities) come from there and the e2e wait bounds derive from its timing envelope.

## CI

PRs run `make vet`, `make build`, `make chart-lint`, `make test-chart`, a generated-files drift check (`make generate raw-manifest` must produce no diff), `make test`, `go test -race ./pkg/... ./cmd/...`, `make test-envtest`, golangci-lint (`ci-lint.yaml` — same version as `make lint`, which also runs it on the go.mod toolchain CI uses: a newer local Go's standard library can change findings or crash the analyzers), CodeQL and `make vulncheck` (`codeql-analysis.yaml`, also daily — govulncheck is a separate job so a vulnerability finding can never skip CodeQL), and a git-hygiene gate (`git.yaml`: every commit message must be a Conventional Commit, no `fixup!`/`squash!` commits). Pushing a `v*` tag builds the image, pushes it to ghcr.io, and publishes both Helm charts as OCI artifacts to `oci://ghcr.io/<owner>/<repo>/{karpenter,karpenter-crd}` (chart version = tag without the `v` prefix, appVersion = tag — the in-repo `Chart.yaml` versions are placeholders overridden at package time, but the release fails fast if they lag the tag: bump both files and run `make raw-manifest` in the release commit). The repository path is lowercased and `helm push` appends the chart name, with no `charts/` segment: every documented install/upgrade command uses `oci://ghcr.io/clevercloud/karpenter-provider-clever-cloud/<chart>` with `--version` and `--namespace`. Commit conventions are documented in CONTRIBUTING.md.

## Operational constraints that shape the code

- Org quota defaults to 40 vCPU / 40 GB RAM **including the control plane**; quota rejections are normal operation, not errors.
- Provisioning takes ~40–90 s; deletion ~40 s.
- The controller must run on nodes karpenter does not manage. The chart (and the `deploy/karpenter.yaml` generated from it) enforces that with a required node affinity on `karpenter.sh/nodepool` **DoesNotExist** — karpenter-core stamps that label on every node it provisions (at registration) and on no other, so the rule holds on `ALL_IN_ONE` (schedulable in-cluster control-plane node), on `DEDICATED_COMPUTE`/`DISTRIBUTED` (control plane outside the cluster, only worker nodes) and on any topology added later. Never re-encode a specific topology's node label as a default: `clever-cloud.com/cluster-node-role: control-plane` was that bug, and `test/chart` fails if it comes back. Before registration, and for good on a resized group's extra node, the node lacks the label and only the `karpenter.sh/unregistered:NoExecute` taint keeps the controller off, so the chart's default tolerations must never cover it (also pinned by `test/chart`).
- Don't enable CKE's own `autoscalingEnabled` alongside this provider (two autoscalers fighting).
