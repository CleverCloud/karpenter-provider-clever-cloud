# Changelog

## 0.13.0 - 2026-10-01

No outbound HTTP, no EUR, and no more decisions karpenter-core cannot see. The pricing refresher is gone — its product endpoint started answering 401, so it had silently failed on every install — and offering prices become a unitless ratio of each flavor's CPU and memory: the controller now talks to nothing but the cluster's Kubernetes API. The provider stops keeping state the scheduler is blind to: quota rejections and refused flavors reach it as unavailable offerings, the create lock is released when the operator acknowledges a NodeGroup (about 1 s) instead of after a 15 s window that every healthy launch timed out on, a transient upstream error no longer reads as a refusal, and a node that an external resize leaves without a provider ID can no longer freeze karpenter-core's cluster state at the next controller restart. Instance types advertise `topology.kubernetes.io/region`, so a region selector stops launching node after node; the catalogue carries the memory measured on today's node image; and an upgrade from v0.12.0 neither halts provisioning on a legacy NodeClass label nor replaces nodes for a label that never reached them. Built on karpenter-core 1.14.1 and the Kubernetes 1.37 client libraries, and validated end to end on a live CKE 1.37 cluster.

### ✨ Added

- **`feat(nodegroup)`: launched NodeGroups are watched until the operator syncs them** — the provider read a NodeGroup's status only inside its acceptance poll, while the VM is created long after it: a refusal published later, a group stuck in `Creating` or a silent operator produced no signal at all until karpenter-core's 15-minute registration TTL. A watch-driven controller now follows every managed NodeGroup whose NodeClaim is launched but not registered. A late terminal refusal fails the launch at once — the quota backoff or flavor hold-out is recorded, the existing rejection counters and events move, and the NodeClaim is deleted (after an uncached confirmation, never once registered) so karpenter re-plans; a persisting transient upstream error is surfaced; and a group still not synced 5 minutes after creation is counted by the new `karpenter_clevercloud_nodegroup_sync_overdue` gauge and reported by a `NodeGroupSyncOverdue` event. The runbook no longer tells operators of worker-only topologies to inspect a control-plane VM they cannot reach.

- **`feat(cloudprovider)`: quota-rejected and refused flavors are unavailable to the scheduler** — karpenter-core keeps no memory of an `InsufficientCapacityError`; the only thing its scheduler reads is `Offering.Available`, which the provider hard-coded to `true`. Near the organisation quota the scheduler therefore rebuilt the same over-quota claim forever while a global, size-blind 60 s backoff fast-failed even a flavor that would have fit, and drift or consolidation replacements looped every few seconds. A quota rejection of a flavor now marks it unavailable for a minute and every larger flavor for two, while smaller flavors stay available, a refused flavor is reported unavailable for its hold-out, and no instance type is ever removed (which would drift running nodes). Pods that fit a smaller flavor get a node; pods only the rejected size can hold stay `Pending` with a scheduling error instead of cycling through failed NodeClaims. The documentation no longer claims that core "relaxes to other options" on its own.

### 🔄 Changed

- **`feat(pricing)!`: the public pricing API refresher is removed** — `GET /v4/kubernetes-product` now requires authentication, so the refresher enabled by default failed on every cycle, never even reached the still-public price-system endpoint, and stayed invisible to the documented staleness alert, which only fires after a first success. The refresher, its controller, its metrics and its configuration are gone: the catalogue is the built-in flavor table plus `settings.flavors` overrides, and the controller needs no egress at all. ⚠️ **Breaking**: the `settings.pricing` chart values and the `PRICING_REFRESH_ENABLED`, `PRICING_REFRESH_PERIOD`, `PRICING_API_URL`, `PRICING_PRODUCT_URL`, `PRICING_PRICE_SYSTEM_URL` and `CLEVER_CLOUD_TOPOLOGY` environment variables are removed (old values are ignored, so an upgrade carrying them still renders); delete the alerts and dashboards built on `karpenter_clevercloud_pricing_refresh_failures_total` and `karpenter_clevercloud_pricing_last_successful_refresh_timestamp_seconds`; to keep a flavor out of provisioning, add a `node.kubernetes.io/instance-type` `NotIn` requirement to the NodePools.

- **`feat(instancetype)!`: flavors are priced by their relative CPU and memory size** — offering prices are now a unitless cost relative to the smallest flavor, `1/3 × cpu/cpu(2XS) + 2/3 × memory/memory(2XS)` (2XS = 1.0), computed from each flavor's own sizing — including flavors added through overrides, which no longer need a price. Weighting memory twice as much as CPU per nominal GB reproduces the ordering of CKE's public worker prices exactly: no provisioning or consolidation decision differs from the EUR prices over every combination of up to four nodes, where equal weights would have inverted twelve. An unpriced or zero-priced override can no longer capture every cheapest-first decision. ⚠️ **Breaking**: `settings.flavors` entries no longer accept `priceHourly` — remove it before upgrading (helm refuses it; with `--reuse-values` pass the corrected list explicitly), and an overrides file mounted outside the chart that still sets it is refused as a whole (`karpenter_clevercloud_instancetype_flavors_config_invalid` = 1). karpenter-core's `karpenter_nodepools_cost_total` and the `savings` of its disruption logs and events now count 2XS-equivalents, not EUR: rescale dashboards, alerts and any NodeOverlay absolute price or fixed price adjustment.

- **`fix(nodegroup)`: the create lock is released as soon as the operator acknowledges the group** — the acceptance poll waited up to 15 s for `Ready`, which arrives 38–58 s after creation, so every healthy launch timed out while holding the global create lock: launches were serialized 15 s apart, `nodegroup_acceptance_timeouts_total` fired on 100% of them, and because karpenter-core's cluster state stays unsynced while a claim has no provider ID, a scale-up froze every disruption cluster-wide and consumed the queued claims' registration TTL. Measured live, the operator's first status write (~1 s) already is its decision — `Creating` + `ReconcileInProgress` when accepted, `QuotaExceeded` directly when rejected — so the poll now returns on that acknowledgement. `Create` drops from 15.06 s to about 1 s, the acceptance-timeout counter stays at 0 on a healthy cluster (its documented alert finally means "the operator did not even acknowledge"), and a hold-out recorded by a late refusal during a launch's own poll survives that launch's acknowledgement.

- **`fix(nodegroup)`: `karpenter.sh` labels stay out of the immutable NodeGroup spec** — the provider copied `karpenter.sh/nodepool` into a NodeGroup's immutable `spec.labels`, which the platform applies to every node of the group. The extra node of an externally resized group, deliberately left without a provider ID, therefore carried it, and karpenter-core ignores such a node while waiting for every node before its first sync: at the next controller restart, provisioning and disruption stopped cluster-wide until the resize was reverted (4 minutes reproduced live). The `karpenter.sh` domain is no longer pushed into the spec (registration still syncs it onto the node), CleverNodeClass labels in that domain are rejected at admission, and for groups created before this release the provider removes `karpenter.sh/nodepool` from a node it refuses a provider ID. Verified live: a restart with a resized group stays synced and provisions within 4 s.

- **`fix(nodegroup)`: a transient upstream error is in progress, not a refusal** — any `ReconcileFailed=True` was terminal, checked before `Ready`. The operator also uses it with reason `UpstreamError` for transient Clever Cloud API failures it retries, alongside `Ready` and `ReconcileInProgress`, so a platform incident deleted groups mid-reconcile, held out one flavor after another until none was left, and could delete a `Ready` VM on the adoption path. `UpstreamError` is now transient — no delete, no hold-out, a `NodeGroupTransientFailure` event instead of `NodeGroupRejected` — and `Ready` always wins; unknown reasons stay terminal.

- **`fix(instancetype)`: instance types advertise `topology.kubernetes.io/region`** — only the zone was advertised and nothing ever put the region on a node, so a pod selecting the region, a StorageClass or PersistentVolume keyed on it, or a NodePool requiring it made karpenter launch a node, find the pod unschedulable there, and launch another (one pod caused three VMs live, stopped only by the NodePool limit). New nodes now carry the region from registration, existing NodeClaims are not drifted, and the README gives the command to label nodes launched before the upgrade.

- **`fix(apis)`: the NodeClass hash covers only delivered labels, and legacy NodeClasses stay `Ready`** — v0.12.0 accepted keys that merely contain `kubernetes.io/` (such as `app.kubernetes.io/part-of`), which the tightened label rule now rejects: after an upgrade such a NodeClass would have gone `NotReady` and stopped provisioning, and removing the key — which never reached any node — would have replaced the whole fleet. The hash now covers only the labels delivered to NodeGroups (hash version `v3`, migrated in place), and labels v0.12.0 accepted keep the NodeClass `Ready`, still filtered from nodes, reported by a `LabelsIgnored` condition and event. ⚠️ Upgrade note: upgrade the controller first and remove such keys only once the condition's reason is `LegacyLabelKeys` (every NodeGroup then carries hash version `v3`); removing them before or together with the upgrade drifts the nodes v0.12.0 built.

- **`fix(nodeclass)`: a NodeGroup's hash is migrated only when its NodeClass spec is unchanged** — a hash-version migration re-stamped every older NodeGroup with the hash of the current spec, so a NodeClass edit that landed while no leader evaluated it was recorded as if the existing nodes had been built with it and never drifted. Each hash generation is now kept, and an older stamp is migrated only when it matches that generation's hash of the current spec; otherwise the node drifts as it should. ⚠️ Upgrade note: from v0.11.x or earlier, a NodeGroup whose NodeClass was edited after it was created now drifts and is replaced under the disruption budgets.

- **`fix(instancetype)`: memory measured on today's node image, and capacity reports bounded to managed nodes** — the built-in sizing overstated kernel-visible memory by 4.4–5.0% on the current CKE image (L and XL had never been measured), so until a node of a flavor reported, karpenter packed pods that the real node could not hold. Every flavor now carries its measured memory, and the e2e suite fails if a provisioned node departs from it by more than 1%. Observed capacity is only accepted from nodes of NodeGroups the provider created whose flavor matches, within 10% of the catalogue, and aggregated by minimum: a kubelet can no longer rewrite the catalogue for every flavor, and mixed images no longer make it oscillate. Refused reports are counted by `karpenter_clevercloud_instancetype_observed_capacity_rejections_total`. Prices move by at most 0.6% with no change to any decision.

- **`fix(instancetype)`: override flavors the platform cannot create are rejected** — the NodeGroup CRD only accepts its own flavor names, so an override such as a case typo (`2xs`) or an invented name entered the catalogue, could win cheapest-first, and was then refused by the API server on every launch as a plain error that core retried until its launch timeout, forever. Override names must now follow the platform's naming (helm rejects others at install time), and an admission refusal is a typed flavor refusal: held out, unavailable to the scheduler, and an `InsufficientCapacityError` so core re-plans elsewhere. ⚠️ Upgrade note: a `settings.flavors` entry with such a name now fails `helm upgrade`.

- **`fix(cloudprovider)`: launch preconditions are re-checked under the create lock** — the NodeClass readiness and termination checks and the flavor choice ran before the create lock was taken, so a claim queued behind it could still launch a flavor the previous claim had just seen refused, launch from a NodeClass that had started terminating, or launch for a NodeClaim deleted while it waited. They now run under the lock, immediately before the NodeGroup is created, with uncached reads of the NodeClaim and NodeClass.

- **`chore(deps)`: Go 1.26.5 → 1.26.8** — go1.26.5 carried five standard-library vulnerabilities the controller reaches (GO-2026-6218 in `net/url`, GO-2026-6090 in `crypto/tls`, GO-2026-6089 and GO-2026-5026 in `net/http`, GO-2026-5972 in `encoding/asn1`). The Dockerfile builder is pinned to the same release as `go.mod`, and a test fails if the two pins diverge.

- **`chore(deps)`: karpenter-core 1.14.0 → 1.14.1, Kubernetes client libraries 0.36 → 0.37, controller-runtime 0.24 → 0.25** — karpenter-core 1.14.1 is a patch release (savings estimates ignore incompatible offerings, cached virtual pod definitions); the vendored `karpenter.sh` CRDs are unchanged. envtest now runs against a Kubernetes 1.37 apiserver, matching the client libraries and the CKE clusters.

### 📚 Documentation

- **`docs`: upgrade, chart path and quota sizing guidance** — the documented `helm upgrade --reuse-values` kept the previous release's defaults, so v0.12.0's controller placement fix never reached an upgraded worker-only install: upgrades now use `--reset-then-reuse-values` (Helm ≥ 3.14). Chart references match what the release publishes, the quota arithmetic is corrected (a 3-node `S` control plane uses 36 GB, not 24), `large-instances` gets limits that admit the flavors it advertises, and the observability runbook is linked from the README and the installation guide.

- **`docs(e2e)`: the live validation of this release is recorded** — `docs/E2E-RESULTS.md` records the run on Kubernetes 1.37: `make e2e` 5/5, the operator's acknowledgement timeline, an upgrade from v0.12.0 (hash migrated without drift, label removed from a resized group's extra node, restart without a stall) and the region selector, with a before/after table.

### 🤖 CI

- **`ci(codeql)`: govulncheck runs in its own job** — as a step ahead of `codeql init` it failed the job first, which switched Go code scanning off for exactly as long as a known vulnerability stayed open. It is now a separate `Govulncheck` job, pinned through `make vulncheck`. ⚠️ If "Analyze Go" is a required status check, add "Govulncheck".

- **`chore(make)`: lint runs on the toolchain `go.mod` pins** — on a newer local Go, golangci-lint's staticcheck crashed on the standard library; `make lint` now uses the `go.mod` toolchain (golangci-lint 2.14), and the contributing guide lists every check CI runs.

- **`test`: destructive-path guards are pinned and NodeGroup payloads are validated against the live schema** — envtest now installs a snapshot of Clever Cloud's real NodeGroup CRD instead of a schema-less stand-in, and the guards mutation testing showed untested (terminating NodeGroups read as gone, the informer-lag guard, repair policies, the GC's fail-closed confirmations, backoff expiry through an injected clock) now fail a test when reverted.

- **`test(e2e)`: the harness fails fast and checks its cleanup again** — the suite stops at once when the controller process dies, runs on free ports so several suites can run side by side, fails on an ownerless NodeGroup that reappears during cleanup, and looks again for the run's NodeGroups after a configurable delay (`E2E_CLEANUP_RECHECK`).

- **`chore(deps)`: GitHub Actions** — `github/codeql-action` 4.37.6 and `actions/stale` 11.

## 0.12.0 - 2026-07-28

Every CKE topology, and nothing silently destructive. The controller is no longer pinned to a node role that exists only on `ALL_IN_ONE`: it is kept off the capacity Karpenter manages by a rule that names no topology, so it also schedules on `DEDICATED_COMPUTE` and `DISTRIBUTED` — where it previously sat `Pending` forever while `helm install` reported success. Three paths that ended in destroyed or stranded capacity are closed: a provider ID is never stamped on more than one node of an externally resized NodeGroup, a change to the NodeClass hash migrates existing NodeGroups instead of replacing every node in the fleet, and an upstream refusal is terminal instead of burning a 15-minute registration TTL on the same flavor. The flavor catalogue no longer depends on getting a per-cluster topology setting right, SIGTERM shuts the controller down cleanly, and the release pipeline runs the full pull-request check set before publishing anything. Built on karpenter-core 1.14.

### 🔄 Changed

- **`fix(providerid)`: an externally resized NodeGroup no longer gets its nodes destroyed** — the provider ID names the NodeGroup, which identifies a single node only while the 1 NodeClaim = 1 NodeGroup invariant holds. When something outside karpenter resizes a managed group (the platform's alert-driven scaler through an inherited `autoscalingEnabled`, a human, anything with `nodegroups/scale` RBAC), every node of the group was stamped with the *same* provider ID. karpenter-core then matches several Nodes to one NodeClaim, sets `Registered=False/MultipleNodesFound` — terminal, registration never retries — and liveness deletes the NodeClaim 15 minutes later, taking the whole NodeGroup and every VM in it. The garbage collector deliberately only *surfaces* an external resize (`nodegroup_external_resizes`, `NodeGroupExternallyResized`) and never fights it; this turned that surfaced anomaly into a destructive one. The controller now refuses to stamp a node when another node of the same group already carries that provider ID, so **exactly one** node keeps it and the extras are left inert. The check is on the Nodes that exist rather than on `spec.nodeCount`: that field is desired state, and on the recovery path (revert the resize to 1) the extra Node object survives ~40 s while its VM is torn down, long enough for a cordon, a drain or a kubelet heartbeat to re-create the collision. That check reads the API server, not the informer cache: reconciles are serialised, so the previous node's patch is already committed when the next one starts, but a cached read could still show the ID free and stamp both. Reproduced live: after `kubectl patch nodegroup --type=merge -p '{"spec":{"nodeCount":2}}'`, the second node received the identical `clevercloud://<ng>` and kept the `karpenter.sh/unregistered:NoExecute` taint indefinitely.

- **`fix(controller)`: SIGTERM now shuts the controller down cleanly** — karpenter-core installs no signal handler (`operator.NewOperator()` roots its context in `context.Background()`, and nothing in the module calls `signal.Notify`), so SIGTERM took Go's default disposition and killed the process outright. controller-runtime never ran its shutdown sequence, which made the `LeaderElectionReleaseOnCancel: true` the operator asks for unreachable: every `helm upgrade` or node drain left the replacement pod waiting out the full 15 s lease with no provisioning, drift evaluation or garbage collection happening. In-flight work was cut mid-flight too — a NodeGroup `Create` could die between the API call and its acceptance poll, leaving the quota-rejection cleanup unexecuted until the next GC sweep.

- **`fix(apis)`: a NodeClass hash change no longer replaces the whole fleet** — `CleverNodeClass.Hash()` is the sole drift signal, and it had two problems. It distinguished `labels: {}` from an absent `labels` (hashstructure skips a nil map but hashes an empty one), so deleting that no-op line — which 9 of the 10 shipped examples carry — replaced every node backed by the NodeClass. And more broadly, **any** change to `CleverNodeClassSpec` moved the hash of every existing NodeClass: `IgnoreZeroValue` does *not* absorb an added field, even one left unset (verified). Adding a single field to the spec would therefore have rolled every fleet, for no configuration change at all. Empty collections are now normalised before hashing, and the hash carries a generation: NodeGroups are stamped with `karpenter.clever-cloud.com/clevernodeclass-hash-version`, `IsDrifted` only compares hashes of the same generation, and the nodeclass controller re-stamps older ones — keeping the hash of a NodeClaim that is already `Drifted`, so a replacement in flight is not silently cancelled. This mirrors karpenter-core's own `karpenter.sh/nodepool-hash-version` mechanism. ⚠️ **For maintainers**: bump `NodeClassHashVersion` in the same commit as any change to `CleverNodeClassSpec` or to the hashing — `TestHashVersionPinnedToSpec` fails until you do.

- **`fix(ci)`: a release can no longer publish untested or truncated artifacts** — two defects that composed. `make raw-manifest` redirected a command group straight into `deploy/karpenter.yaml`, so the file was truncated before `helm template` even ran, and the group's exit status was that of the trailing `sed`, which always succeeds: a helm failure left the shipped manifest as an 8-line header — a namespace and nothing else — while `make` exited 0. And the release workflow triggers on `push: tags`, while `ci`/`ci-test`/`ci-lint` trigger only on branches and pull requests, so a tag push ran **no** tests, lint or generated-files check — the very check whose failure message tells maintainers to run `make raw-manifest`. The manifest is now rendered to a temp file and moved into place only on success, the Makefile runs under `bash -eu -o pipefail` so no recipe can mask a failure again, and the release job runs the full PR check set plus a drift check before publishing anything.

- **`fix(test)`: the e2e quota scenario no longer flakes on a healthy cluster** — `QuotaFastFail` waited for the *cumulative* `nodegroup_quota_rejections_total` to reach 1, with no baseline taken at scenario start. The scenarios share one controller process, and `docs/e2e.md` says so explicitly ("serial — they share the org quota"), so any earlier scenario that touched the quota — normal operation near the ceiling — satisfied the wait at t=0, before the ReplicaSet had created a single pod. The scenario then read `0/0 pods Pending` and failed on a perfectly healthy cluster. Observed exactly that during a parallel validation campaign. It now asserts a delta from a baseline taken before the workload exists, the way the unit tests already do through `pkg/metrics/metricstest`, and polls the pod list instead of reading it once.

- **`feat(pricing)`: the flavor catalogue no longer depends on getting `CLEVER_CLOUD_TOPOLOGY` right** — the refresher took one topology's `availableFlavors`, defaulting to `DISTRIBUTED`, which is wrong on two of the three CKE topologies. Measured on live clusters, those per-topology lists are a **product listing, not an admission rule**: an `ALL_IN_ONE` cluster advertises only `S…XL` yet provisions `2XS` NodeGroups without complaint. Pinning a topology could therefore only ever *shrink* a working catalogue, and "fixing" the setting to match your cluster would have dropped flavors that work — rolling every node running one of them through the drift path. The default is now the **union of every topology's list**, so no per-cluster setting is required and a topology CKE adds later enters the catalogue on its own. `CLEVER_CLOUD_TOPOLOGY` / `settings.pricing.topology` remain as an *optional* restriction; a value that does not exist upstream still fails every refresh loudly instead of degrading quietly. This is only safe alongside the terminal-refusal change above: if the platform ever does enforce the lists, a refused flavor fails fast and is held out of provisioning rather than looping every registration TTL.

- **`fix(nodegroup)`: an upstream refusal that is not a quota rejection is now terminal** — `waitForAcceptance` recognised exactly two outcomes, `QuotaExceeded` and `Synced`. Any other `ReconcileFailed` — a flavor the cluster cannot provision, a spec the operator will not accept — was indistinguishable from "still reconciling": the poll timed out, `Create` reported optimistic success, and the launch burned karpenter's full 15-minute registration TTL before re-planning onto the very same flavor, forever, with the operator's own explanation surfaced nowhere. Such a refusal now frees the reservation and fails the launch as an `InsufficientCapacityError`, carrying the upstream reason and message on a `NodeGroupRejected` event and counted by `nodegroup_rejections_total`. Because karpenter-core keeps no per-offering memory of an ICE, the refused flavor is additionally held out of `resolveInstanceType` for 5 minutes so the re-plan lands on a different one; it is released as soon as the same flavor is accepted again.

- **`chore(deps)`: karpenter-core 1.13.0 → 1.14.0** — the vendored `karpenter.sh` CRDs are re-synced (`make generate`); the only schema change is the `NodePool.spec.disruption.consolidationPolicy` enum gaining `Balanced`. ⚠️ That widening is a one-way door: a NodePool that adopts `Balanced` becomes invalid if the CRDs are ever rolled back to 1.13. Two upstream behaviour changes are worth knowing even though neither needs a provider change: consolidation now sorts candidates by price-per-disruption **descending** (the most expensive nodes are considered first, which near the org quota means more quota rejections during consolidation), and `consolidateAfter` now also blocks a node as a consolidation **destination**, not only as a candidate — so a large `consolidateAfter` gives up packing onto existing nodes, leaving empty-node deletion and replace-with-a-new-node. Validated on live CKE clusters: `make e2e` 5/5 on both an `ALL_IN_ONE` and a worker-only topology, with timings unchanged.

- **`fix(charts)`: the controller is schedulable on every CKE topology, not just `ALL_IN_ONE`** — the chart pinned the controller with `nodeSelector: clever-cloud.com/cluster-node-role: control-plane`. That label only exists on `ALL_IN_ONE`, where the control plane is made of in-cluster nodes. On `DEDICATED_COMPUTE` and `DISTRIBUTED` the control plane runs on VMs outside the cluster and every node is a worker, so **no node ever matched**: `helm install` reported success, every object was created, and the controller sat `Pending` forever while nothing was ever provisioned — silently, on two of the three topologies. The default is now `nodeSelector: {}` plus a required node affinity on `karpenter.sh/nodepool` **DoesNotExist**. karpenter-core stamps that label on every node it provisions and on no other, so the placement guarantee that motivated the original selector — *never run on capacity Karpenter can deprovision* — is preserved verbatim while naming no topology, and therefore keeps holding for topologies added later. A `karpenter.sh/unregistered:NoExecute` toleration is deliberately **not** granted, so the brief pre-registration window stays closed. `test/chart` (`make test-chart`, wired into PR CI) fails if a topology-specific node label comes back as a chart default.

  ⚠️ **Behaviour change for existing installs.** On `ALL_IN_ONE` the controller pod is recreated and may move off the control-plane node onto any other node Karpenter does not manage. Nothing is *relying* on control-plane pinning for correctness — the invariant was always "not on Karpenter's own nodes", and the new rule states exactly that — but if you deliberately want the controller on control-plane nodes (co-location with the API server, a dedicated maintenance window), set it back explicitly: `--set nodeSelector."clever-cloud\.com/cluster-node-role"=control-plane`. That still ANDs with the affinity, so the guarantee is not weakened.

- **`fix(charts)`: default tolerations** — the controller now tolerates `node-role.kubernetes.io/control-plane:NoSchedule`. No CKE node role is tainted today, so this is a no-op; it is shipped so that a topology which starts tainting the only nodes the controller could run on cannot reproduce the same silent-`Pending` failure. It grants no access to Karpenter-managed nodes, which are excluded by affinity rather than by a taint.

- **`fix(test,examples)`: the e2e suite and the example workloads no longer assume `ALL_IN_ONE`** — both selected `clever-cloud.com/cluster-node-role: worker` to keep pods off pre-existing capacity. That only works where the sole non-Karpenter node is the control plane; on `DEDICATED_COMPUTE`/`DISTRIBUTED` the pre-existing pool is worker nodes too, so pods landed on it, no NodeClaim was created, and the suite failed on a healthy cluster while the examples silently demonstrated nothing. Both now require `karpenter.sh/nodepool` to **exist** — the exact dual of the chart rule.

## 0.11.0 - 2026-07-10

Pre-GA hardening: this release makes the provider loud and provable. Every known failure path — quota races, vanished NodeGroups, the public pricing API, a broken flavors file, a flavor leaving the catalogue — now degrades locally with a metric and an event instead of failing silently or cluster-wide; destructive garbage collection requires proof of ownership; and the behavioral claims are continuously verified by an envtest stage in PR CI plus a local end-to-end suite automating the live-cluster campaigns. Built on karpenter-core 1.13.

### ✨ Added

- **`feat(observability)`: provider metrics, Kubernetes events and call instrumentation** — every provider failure path now has a signal: `karpenter_clevercloud_*` Prometheus series (quota rejections, acceptance timeouts, vanished groups, GC reaped/refused, external resizes, pricing refresh health, unknown-flavor lookups — pre-seeded so `increase()`-style alerts see the very first tick), Kubernetes events on the objects operators actually describe (NodeClaim, NodeGroup), and karpenter-core's cloudprovider decorator for per-method durations and typed errors. What each signal means and what to do when it moves is documented in the `docs/observability.md` runbook.
- **`test`: automated integration and end-to-end suites** — the behavioral claims of `docs/E2E-RESULTS.md` stop relying on ad-hoc manual re-validation. `make test-envtest` (now part of PR CI) runs the controllers against a real kube-apiserver: it proves every vendored CRD installs on the targeted Kubernetes version and exercises the admission/finalizer/watch semantics the fake client cannot. `make e2e` runs the full provider against a live CKE cluster — provision, consolidation, drift, both faces of the GC safety net, and quota fast-fail without leaks — with layered cleanup (in-suite plus `hack/e2e-cleanup.sh`) because leaked NodeGroups bill hourly. The e2e stage is deliberately local-only: CKE test clusters are ephemeral and cluster-admin credentials stay out of CI. Setup and semantics in `docs/e2e.md`.

### 🔄 Changed

- **`fix(gc)`: reaping requires a verified NodeClaim owner — the managed label alone is never sufficient** — the marker label is forgeable by hand-copying a karpenter-created manifest, and the mutable labels are not an identity: the GC now only deletes a NodeGroup after verifying the NodeClaim owner reference stamped at creation, never while any owner-named claim is still alive, and otherwise refuses loudly (`gc_refused_nodegroups` gauge + hourly `GarbageCollectionRefused` event) instead of guessing.
- **`chore(deps)`: karpenter-core 1.12.1 → 1.13.0, with the vendored `karpenter.sh` CRDs now synced automatically from the pinned module** — `make generate` refreshes them (`sync-karpenter-crds`) and CI fails on drift, so the CRDs can no longer silently lag the module. Go moves to 1.26.5 (crypto/tls fix) with grouped `k8s.io/*` bumps.
- **`fix(deploy)`: `deploy/karpenter.yaml` is generated from the Helm chart** (`make raw-manifest`, CI fails on drift) — the raw manifest and the chart can no longer disagree about what a default install looks like; never edit it by hand.
- **`fix(pricing)`: the public price API is no longer trusted blindly** — a refresh is now rejected (keeping the last-known-good catalogue) when the currency is not EUR, the RAM countable is not priced per 10⁹ bytes, a node service carries more than one price plan (tiered first-tier-free plans are the platform norm on other services and `price_plans[0]` would read the free tier), a rate is non-positive, or a rate drifts more than an order of magnitude from the built-in defaults. Response bodies are capped at 1 MiB. `NominalGB` stays seed-side by design: the API never exposes sizing — `settings.flavors` is the mitigation for an upstream re-spec.
- **`feat(pricing)`: fleet etiquette on the public API** — refresh requeues are jittered ±10% so platform-wide controller restarts don't synchronize every cluster's polling, and requests carry a `karpenter-provider-clever-cloud` User-Agent so platform support can attribute the traffic.
- **`fix(nodeclass)`: readiness now proves the cluster is a CKE cluster** — a new `NodeGroupAPIServed` condition probes that `nodegroups.api.clever-cloud.com` is actually served, so on any other cluster the NodeClass stays not-Ready with a readable condition instead of failing at the first Create; `Create` additionally requires Ready to be affirmatively True (an Unknown readiness no longer launches machines), and `CleverNodeClass.Hash()` panics loudly on a future un-hashable spec change instead of silently hashing every NodeClass to the same value. ⚠️ Upgrade note: launches racing the first reconcile of each existing NodeClass after the upgrade may be fast-failed once and retried (the new condition starts Unknown until the controller stamps it).
- **`fix(nodegroup)`: launches whose NodeGroup vanishes fast-fail instead of burning the registration TTL** — the quota engine reclaiming an accepted group (the documented upstream race) previously left the NodeClaim waiting out karpenter's 15-minute registration TTL. A vanish observed during the acceptance poll now fails the Create immediately, and the GC sweep deletes launched-but-unregistered NodeClaims whose NodeGroup is gone (2-minute informer-lag guard; never-synced-but-present groups are deliberately left alone). Surfaced via `nodegroup_vanished_total` and a `NodeGroupVanished` event on the NodeClaim.
- **`feat(gc)`: external resizes of managed NodeGroups are surfaced** — the 1 NodeClaim = 1 NodeGroup invariant assumes nobody else writes `nodeCount`, but the CRD exposes a scale subresource and the platform's alert-driven scaler can inherit `autoscalingEnabled`. The GC sweep now flags managed groups whose nodeCount is not 1 (`nodegroup_external_resizes` gauge + hourly `NodeGroupExternallyResized` event) — surfaced, never fought.
- **`fix(instancetype)`: an invalid `settings.flavors` file no longer crashloops the controller** — the chart rolls the pod on every flavors change, so a typo converted directly into CrashLoopBackOff of the platform's autoscaler. The controller now degrades to the base catalogue without the overrides, surfaced via the `flavors_config_invalid` gauge and an error log; the chart additionally validates `settings.flavors` at install/upgrade time through values.schema.json.
- **`fix(gc)`: destructive decisions are confirmed against the API server, and one stuck object no longer blocks the sweep** — reaping a NodeGroup (a VM) or writing off a vanished launch was decided from the informer cache alone; both are now confirmed with an uncached read before acting, and Delete failures are collected instead of aborting the sweep, so one stuck object cannot shield the others until the next pass.
- **`fix(cloudprovider)`: a flavor leaving the catalogue no longer degrades the whole cluster** — `Get`/`List` now serve NodeGroups whose flavor left the served catalogue (upstream removal, topology change, removed override) with a synthesized instance type instead of erroring, so karpenter-core's NodeClaim garbage collection and node termination keep working. The synthesized type never enters the provisioning catalogue; the affected nodes are replaced through karpenter-core's `InstanceTypeNotFound` drift path, paced by the NodePool's disruption budgets. Semantics documented in `docs/observability.md`.
- **`fix(instancetype)`: an override introducing a flavor outside the built-in catalogue must now set `cpu`, `memoryKi` and `priceHourly`** — previously an unpriced new flavor was silently accepted at 0 EUR/h and captured every cheapest-first provisioning decision. ⚠️ Upgrade note: a `settings.flavors` entry that relied on this (new-name flavor without `priceHourly`) now fails override loading — the controller degrades to the base catalogue without any override and raises `flavors_config_invalid`; add the missing price before upgrading. An override resurrecting a seed flavor absent from the live catalogue is still accepted, but logged loudly.

## 0.10.0 - 2026-06-18

CKE flavor prices and the available-flavor list can now refresh automatically from Clever Cloud's public, token-less pricing API — **enabled by default**. The built-in static catalogue stays as the fallback, and `settings.flavors` becomes a per-flavor overlay that coexists with the refresher and always wins.

### ✨ Added

- **`feat(pricing)`: dynamic flavor-catalogue refresher** — a 12 h singleton (`PRICING_REFRESH_PERIOD`) resolves the per-resource rates (`/v4/billing/price-system`, keyed by `zone_id = CLEVER_CLOUD_REGION`) and the available-flavor list for `CLEVER_CLOUD_TOPOLOGY` (`/v4/kubernetes-product`) from Clever Cloud's public, unauthenticated API, recomputes each flavor price (`cpu × vcpu_rate + nominalGB × ram_rate`) and swaps the catalogue. cpu/memory sizing is not exposed by the API, so it stays seeded statically and keeps self-correcting at runtime from observed node capacity. A failed refresh keeps the last-known-good catalogue and retries sooner; it never blocks startup.
- **`feat(charts)`: `settings.pricing`** — `enabled` (default `true`), `refreshPeriod`, `apiURL`, `topology`, and independent per-endpoint `kubernetesProductURL` / `priceSystemURL` overrides, mirrored as `PRICING_*` / `CLEVER_CLOUD_TOPOLOGY` env in `deploy/karpenter.yaml`.

### 🔄 Changed

- **The refresher is enabled by default** — a default install now makes outbound HTTPS to `api.clever-cloud.com` (still token-less, no credentials). Set `settings.pricing.enabled=false` to keep the controller fully in-cluster; the binary's own `PRICING_REFRESH_ENABLED` gate still defaults off as a safe fallback.
- **`settings.flavors` is now a per-flavor overlay**, not a full replacement — every field except `name` is optional, set values win per field over the base/dynamic catalogue, and the overrides are re-applied after each refresh. (The replace-everything override shipped only after `v0.9.2` and was never released.)

## 0.9.0 - 2026-06-11

Initial release: a [Karpenter](https://karpenter.sh) cloud provider for Clever Kubernetes Engine (CKE). Every operation goes through the cluster's own in-cluster NodeGroup API (`nodegroups.api.clever-cloud.com/v1`) — no Clever Cloud HTTP client, no API token to manage. Validated end-to-end against live CKE clusters ([docs/E2E-RESULTS.md](docs/E2E-RESULTS.md)): node registered in ~44 s end-to-end, consolidation, drift and organisation-quota behaviour all exercised on real hardware.

### ✨ Added

- **`feat(cloudprovider)`: the karpenter `CloudProvider` implementation** (9816d44). One NodeClaim = one dedicated `nodeCount: 1` NodeGroup named after it; provider IDs are `clevercloud://<nodegroup>`; drift detection through the CleverNodeClass hash annotation stamped at creation; organisation-quota rejections map to karpenter's `InsufficientCapacityError` so the scheduler relaxes to other options instead of waiting out the 15-minute registration TTL; terminating NodeGroups read as NotFound so the Clever Cloud finalizer can complete once karpenter releases the node.
- **`feat(nodegroup)`: quota-aware NodeGroup lifecycle** (ca2dfab). Creations are serialized and polled up to 15 s for upstream acceptance; a quota rejection deletes the NodeGroup immediately (frees the reservation) and arms a one-minute fail-fast backoff that any delete clears. Only NodeGroups carrying `karpenter.clever-cloud.com/managed=true` are ever touched — groups created by hand or by CKE's own autoscaler are off-limits.
- **`feat(instancetype)`: static flavor catalog** (ec34228). 2XS through XL with EUR/hour pricing; 2XS/XS/S/M capacities measured on live nodes, L/XL derived estimates self-corrected at runtime from observed node capacity.
- **`feat(controllers)`: four CKE-specific controllers** (61a5a3c). `providerid` stamps `spec.providerID` on nodes (CKE leaves it empty and karpenter matches nodes to NodeClaims through it), `garbagecollection` reaps managed NodeGroups whose NodeClaim is gone, `nodeclass` owns CleverNodeClass validation, readiness conditions and a termination finalizer, `instancetypecapacity` feeds observed node capacity back into the catalog.
- **`feat(apis)`: the two API groups** (92b484d). `CleverNodeClass` (v1alpha1) under `karpenter.clever-cloud.com`, and a deliberately loose hand-written typed client for the Clever Cloud-owned NodeGroup CRD.
- **`feat(charts)`: `karpenter` and `karpenter-crd` Helm charts** (c9fd652) published as OCI artifacts on ghcr.io, plus raw manifests and vendored CRDs under `deploy/` (b16d670).

### 📚 Documentation

- README, getting-started installation walkthrough and the live-cluster E2E validation report (baa8eeb).
- Ten self-contained NodePool/CleverNodeClass examples and seven demo workloads covering the flavor catalog, flavor pinning, pool limits, weighted pools, dedicated team nodes, disruption budgets and node lifetime (8d2f25d).
- Contributing guide and agent instructions, with `AGENTS.md` symlinked to `CLAUDE.md` (c3309a0).

### 🤖 CI
